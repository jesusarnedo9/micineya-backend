# Cuentas y perfil

## Implementado

- Foto de perfil desde el selector de imágenes de Android: recorte cuadrado y compresión en el teléfono. El backend valida contenido, tamaño y dimensiones, recodifica a JPEG de 256 × 256 sin metadatos y limita el resultado a 64 KiB.
- La foto se guarda en una tabla separada (`usuario_foto_perfil`) para no cargarla al validar cada JWT. Una sola imagen por usuario; reemplazarla o quitarla no conserva versiones anteriores en las tablas activas.
- Para una comunidad inicial de 100 cuentas, las imágenes ocupan como máximo unos 8,4 MiB en Base64, más el espacio propio de la base y sus copias de respaldo. No se necesita otro proveedor de almacenamiento para este bloque.
- El avatar con la inicial se mantiene cuando no hay foto.
- El panel **Tu cuenta** está disponible en Perfil y durante la selección de preferencias. Permite cambiar contraseña y eliminar cuenta.
- El cambio de contraseña exige la actual, invalida access y refresh tokens anteriores y vuelve al login.
- El borrado exige contraseña actual y confirmación explícita. Elimina usuario, foto, reseñas, guardadas, preferencias, descartes e historial de recomendaciones. Conserva el catálogo y los datos de otras cuentas.
- Los JWT nuevos incluyen el ID de cuenta. Una cuenta recreada con el mismo email rechaza tokens de la anterior. Los usuarios anteriores al despliegue pueden seguir usando sus tokens sin ID hasta renovar; las nuevas cuentas no aceptan ese formato antiguo.
- La caché local de reseñas de la app usa el ID de cuenta cuando está disponible. Al borrar desde la app, se eliminan esa caché, la antigua basada en email y el identificador recordado. Las respuestas correctas del backend prevalecen sobre copias locales para no restaurar reseñas borradas desde otro dispositivo.

## Página externa de eliminación

Ruta del backend: `/eliminar-cuenta.html`.

Es pública para que pueda abrirse sin la app, pero el borrado requiere autenticación y contraseña. Las credenciales y tokens se mantienen solo durante la solicitud; la página no los guarda en almacenamiento del navegador ni utiliza servicios externos. La recuperación de contraseña pendiente será necesaria para quienes ya no recuerden su clave.

## Contratos de API

- `GET /api/users/me/foto` → `{ "dataUri": null }` o una imagen JPEG Base64.
- `PUT /api/users/me/foto`, cuerpo `{ "base64": "..." }` → imagen normalizada.
- `DELETE /api/users/me/foto` → 204.
- `PUT /api/users/me/password`, cuerpo `{ "passwordActual": "...", "passwordNueva": "..." }` → 204.
- `DELETE /api/users/me`, cuerpo `{ "passwordActual": "..." }` → 204.

Todos estos endpoints exigen la cuenta autenticada y operan exclusivamente sobre ella.

## Despliegue y comprobación corta

1. Desplegar primero el backend. La configuración actual `ddl-auto=update` agrega la tabla de fotos y la columna nullable `usuarios.requiere_token_con_id`; no requiere credenciales nuevas. Antes de producción pública queda pendiente migrar a cambios de esquema versionados.
2. El frontend agrega `expo-image-picker` y `expo-image-manipulator`. Se necesita una nueva compilación Android para distribuirlos en el APK. Se usa el selector del sistema; la configuración bloquea acceso amplio a fotos, micrófono, cámara y almacenamiento.
3. Con una cuenta de prueba, elegir una foto, abrir nuevamente la app y quitarla. Probar cancelar el selector y una conexión interrumpida: la foto anterior debe conservarse si el guardado falla.
4. Cambiar contraseña y comprobar login con la nueva. Borrar solamente una cuenta descartable con reseñas y guardadas; revisar que otra cuenta conserve sus datos.
5. Tras desplegar, abrir `/eliminar-cuenta.html` en el navegador y probar el flujo con otra cuenta descartable.

Las pruebas `CuentaPerfilTests` y `UsuarioServiceLoginTests` cubren autenticación, protección de endpoints, persistencia y límites de fotos, cambio de contraseña, borrado completo, aislamiento entre cuentas y rechazo de tokens de una cuenta recreada. Falta la comprobación visual en el teléfono.

## Preparar el correo para el último bloque

No hace falta contratar otro servidor. El backend puede llamar a la API de un proveedor de correo.

1. Registrar un dominio propio, o usar uno que ya pertenezca al desarrollador. No hace falta contratar hosting web adicional.
2. Crear una cuenta gratuita de Resend y agregar el dominio o un subdominio dedicado a envíos.
3. Copiar en el panel DNS los registros que indique Resend y esperar a que el dominio figure verificado.
4. Elegir un remitente, por ejemplo `MiCineYa <cuentas@tu-dominio>`. Luego se configurará la clave API como secreto en Render, nunca en Git ni en el frontend.

Documentación oficial: [límites de Resend](https://resend.com/docs/knowledge-base/account-quotas-and-limits) y [verificación de dominios](https://resend.com/docs/dashboard/domains/introduction). Consultado el 9 de septiembre de 2026: plan gratuito de 3.000 correos mensuales y 100 diarios. La cantidad de cuentas no equivale a la cantidad de envíos; reenvíos y recuperaciones también cuentan.

La integración de verificación y recuperación sigue pendiente. También quedan por desarrollar amigos, privacidad y moderación social, pochoclos, política de privacidad y la preparación final de Google Play.
